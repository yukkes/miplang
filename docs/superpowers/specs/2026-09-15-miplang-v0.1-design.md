# MIPLang v0.1 Design

## Goal

MIPLang is a lightweight algebraic modeling language for LP/MILP. A model is written once in a `.mip` file, compiled by a Go CLI into a language-neutral canonical IR, and consumed by thin TypeScript, Python, Java, Go, and Rust runtimes. HiGHS is the intended solver backend; v0.1 establishes the language/compiler/runtime boundary before native solver adapters are added.

## Principles

- One mathematical model source of truth; no per-language modeling DSLs.
- Solver-neutral canonical IR with stable versioning.
- Compiler performs parsing, name resolution, type/shape validation, and linearity checks.
- Runtimes stay thin: load IR, bind solver adapters, expose results.
- LP/MILP only in v0.1; no nonlinear expressions or scripting language.
- Permissive licensing and no dependency on AMPL implementation code.

## v0.1 Language Surface

The first vertical slice supports:

- `set NAME;`
- `param NAME[INDEX_SET];` and scalar `param NAME;`
- `var NAME[INDEX_SET] integer >= NUMBER;`
- continuous variables by omitting `integer`
- indexed constraints: `constraint Name[i in SET]: expression <= expression;`
- scalar constraints
- `minimize` and `maximize`
- `sum[i in SET] { expression }`
- numeric literals, symbol references, indexed references, `+`, `-`, `*`, parentheses

v0.1 parses and validates symbolic models. Data binding, numeric flattening, lexicographic objectives, and HiGHS adapters are explicit next milestones.

## Canonical IR

The compiler emits deterministic JSON with `schemaVersion`, declarations, constraints, and objectives. Expressions are structural nodes rather than source strings, so runtimes never need to parse MIPLang syntax.

## Repository Layout

- `cmd/miplang`: CLI entrypoint.
- `internal/lexer`, `internal/parser`: source processing.
- `internal/ir`: canonical IR data model.
- `internal/compiler`: parse + semantic validation + deterministic JSON emission.
- `schema`: canonical IR JSON schema.
- `runtimes/{typescript,python,java,go,rust}`: thin IR loaders and conformance tests.
- `examples`: executable language examples.
- `testdata`: golden inputs/outputs shared by all runtimes.

## Error Model

Compiler errors carry source offset, line, and column and describe the unexpected token or semantic issue. Unknown symbols and unsupported nonlinear products fail at compile time.

## Testing

Go compiler tests follow red-green-refactor. A golden model compiles to deterministic IR. Every runtime has a conformance test that loads the same IR fixture and asserts schema version and model identity. GitHub Actions runs Go, Python, Node, Java, and Rust checks.

## Non-goals for v0.1

- AMPL compatibility.
- `.nl` compatibility.
- Runtime solver adapters.
- Multi-objective/lexicographic solving.
- External data files.
- Nonlinear/quadratic models.
